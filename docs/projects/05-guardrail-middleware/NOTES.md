# P05: GuardrailMiddleware — Notes

## Task 1: PiiRedactor (TDD)

**Pure redactor, order matters.** `PiiRedactor` (src/MafDemo.Core/Guardrails/PiiRedactor.cs) is two `GeneratedRegex` passes over a string — employee IDs (`EMP-\d{4,6}` → `[REDACTED-ID]`) first, then emails (`[\w.+-]+@[\w-]+\.[\w.]+` → `[REDACTED-EMAIL]`). The order is deliberate: an employee ID sitting in an email local part (`EMP-44555@contoso.com`) gets the ID token replaced first, but the email pass then does **not** match the remainder (`[REDACTED-ID]@contoso.com` — the brackets aren't in the local-part class), so the `@contoso.com` domain stays visible; only standalone emails become `[REDACTED-EMAIL]`. The ID — the actual PII — is still caught either way. Pure class in Core, TDD'd before any middleware existed (27/27 solution tests at close).

## Task 2: Run middleware — where it sits, and what redaction touches

**Two middleware types, two intercept points.** Run middleware goes on the agent builder: `baseAgent.AsBuilder().Use(runFunc: ..., runStreamingFunc: null).Build()` — it wraps the *whole run*: it receives the input `IEnumerable<ChatMessage>`, calls the inner agent, and can rewrite both sides. Function-invocation middleware (`Use` extension on `FunctionInvocationDelegatingAgentBuilderExtensions`) wraps *each individual tool call* — it sees an `AIAgent`, a `FunctionInvocationContext`, and a `next` delegate, and hooks the `FunctionInvokingChatClient` that P02's `TicketBot` already puts in the chat pipeline. Order within the run-middleware chain matters too: `Use(Logging)` before `Use(Redaction)` makes Logging the *outer* middleware, so `[log] run start: 1 message(s)` reflects the original pre-redaction input (transcript order log-start → redact → log-end confirms it), while `[log] run end` runs after Redaction's output pass but is unaffected because that pass is in-place.

**Verified API facts (fourth doc-drift instance).** Shipped Microsoft.Agents.AI 1.19.0 has **no named `AgentRunDelegate`** — `AIAgentBuilder.Use` takes the raw `Func<IEnumerable<ChatMessage>, AgentSession?, AgentRunOptions?, AIAgent, CancellationToken, Task<AgentResponse>>`, with session and options nullable (a non-nullable alias compiles but warns CS8620). Only the non-streaming `runFunc` was provided (`runStreamingFunc: null`) — per the package remarks the builder reuses it for `RunStreamingAsync` too, so one func serves both call paths. Each middleware also materializes the incoming sequence with `ToList()` before counting: an `IEnumerable<T>` may be one-shot, and both `Count()` and the inner run enumerate it.

**Redaction mechanics.** Input redaction *clones* every user-role message (`ChatMessage.Clone()` + a fresh `TextContent`) rather than mutating — the caller's message objects are untouched, other roles pass through by reference. It covers **all** user messages, a disclosed strict superset of the brief's "last user message," so session-supplied history is covered too. Output redaction is a clean in-place rewrite of `TextContent.Text` on assistant messages — `TextContent.Text` is settable in 1.19.0 — with `FunctionCallContent`/`FunctionResultContent` untouched and the `Messages` count preserved. The IChatClient-middleware redaction variant (spec stretch) was not built; it would have intercepted each chat call *inside* the tool loop rather than once around the whole run.

**PII leak-surface caveat.** The `[redact] user input: <original> -> <redacted>` echo prints the **original** PII to the console (and any captured transcript). That is a demo-visibility feature, explicitly ruled as such at review — a real deployment would never print raw PII to any sink, not even a logging one. The guardrail protects the *model's* input; the console echo is the one place the raw value survives on this side of the wire.

## Task 3: Function-invocation middleware — approval gate

**Rejection without `next`.** `ToolApprovalMiddleware.Create` (src/P05.GuardrailMiddleware/Middleware/ToolApprovalMiddleware.cs) logs every call (`[tool] <name>`), and only gates the destructive one: name `UpdateTicketStatus` *and* argument `status` = `Closed` (ordinal case-insensitive, so a model sending "closed" is still caught). Everything else — other tools, or the same tool with a non-Closed status — passes straight through. On rejection the middleware **returns a synthetic result string without ever invoking `next`**: `"Rejected by operator approval. Do not close the ticket."` — the model sees that as the tool's result and reacts to it conversationally; the tool never runs. The approval prompt is an injectable `Func<string, bool>` (default: `Console.ReadLine`, `y` approves) so the unit tests approve/reject without a console — 31/31 tests across the whole solution (4 of them in this project), no live agent needed, because `FunctionInvocationContext` has a public parameterless constructor with settable `Function`/`Arguments`. Argument access uses `TryGetValue`: `AIFunctionArguments` is an `IDictionary<string, object?>` with no `GetValue` helper.

**Tool-name gotcha (this one bit me live).** `AIFunctionFactory` **strips a trailing "Async"** when naming tools: P02 registers the method `UpdateTicketStatusAsync` with no name override, so the AIFunction — and the tool definition the model sees — is `UpdateTicketStatus`. Anyone gating tools by name must use the suffix-stripped name; the spec's snake-case `update_ticket_status` maps here too. The cost of getting it wrong is silent: the gate simply never fires. During Task 3's first live run the middleware gated on `"UpdateTicketStatusAsync"`, the comparison never matched, and the ticket closed unapproved — caught only because the middleware's own `[tool] UpdateTicketStatus` log (and the `execute_tool` OTel span) showed the real name. This is the single most P06-relevant fact in the project: gate on what `AIFunction.Name` says, not on what the method is called.

## Task 4: OTel → Aspire dashboard

**Additive telemetry in AgentCommon.** Per controller ruling, `StartOtlp(string serviceName)` was added to the existing `MafDemo.AgentCommon` `Telemetry` class (same `Experimental.Microsoft.Agents.AI` source as P01) instead of a new P05 Telemetry.cs; P01–P04 still call the byte-identical `Start(string)` console path. OTLP over gRPC, default endpoint `http://localhost:4317`, overridable via `OTEL_EXPORTER_OTLP_ENDPOINT`; the dashboard container (`./aspire-dashboard.sh` at repo root) maps host 4317 → its OTLP port 18889.

**What the trace showed.** Live run of the approval scenario: spans `chat` (model call), `orchestrate_tools` (the agent run), and `execute_tool` for both `UpdateTicketStatus` and `AddTicketNote` — service `P05.GuardrailMiddleware`, ActivitySource `Experimental.Microsoft.Agents.AI`, OpenTelemetry SDK 1.17.0 (the exporter package's pinned version, not the Agents SDK). **Zero occurrences of `EMP-44555` in any span** — the redaction middleware rewrote the input before the inner agent ran, so the model's span captured only the redacted text. That is the guardrail proving itself in the telemetry rather than just in the transcript.

**Browser-less span verification.** The Aspire dashboard logs **no per-span receipt line** — `docker logs` is silent about ingestion, so "no output" proves nothing either way. The evidence chain was: live gRPC connection from the P05 process to :4317 (lsof), a 3370-byte relay into the official container's OTLP port with a normal response, then a throwaway second dashboard instance whose `/api/telemetry/traces` API returned the actual decoded spans. So the spans were verified via the dashboard's HTTP API, not via docker logs and not via the UI (no browser was opened; no visual claim made).

## Doc-drift ledger (fifth instance)

P05 hit **two more** spots where the shipped 1.19.0 package XML beat the Microsoft docs: the run-middleware delegate shape (no `AgentRunDelegate`; raw nullable-session Func; single-func streaming reuse) and the function-middleware facts (`Use` is a builder *extension*, not an instance method; `FunctionInvocationContext`'s public settable ctor; `AIFunctionArguments` as plain `IDictionary`). Running total across the repo: **5 verified drift instances** — sessions (P03), MCP, context providers (P04), run middleware, function middleware. The working rule that has now held five times: read the package XML/reflection in `~/.nuget/packages/microsoft.agents.ai.*` (and `microsoft.extensions.ai`) *first*, treat the doc pages as secondary. The verified facts are recorded in the XML-doc comments on `RunMiddlewares`' `RunMiddlewareFunc` alias (src/P05.GuardrailMiddleware/Middleware/RunMiddlewares.cs) and `ToolApprovalMiddleware`'s `FunctionMiddlewareFunc` alias, so the next project inherits them from the code, not from memory.
